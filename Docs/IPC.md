# IPC

M1, M2, and M3+ contract between the Engine (`src/main`) and the App (`src/renderer`). The typed allow-list is `IPC_CHANNELS`, derived in `src/shared/ipc/index.ts` from the per-area channel records in `src/shared/ipc/<area>.ts` (see ARCHITECTURE.md, IPC contract). Behaviour that is not listed here is not part of this contract. The M3+ channels are typed so pipeline, scheduler, queue, headless, tray, email, scheduled reports, export, and the renderer can be built in parallel.

Invokes go renderer to main (`ipcRenderer.invoke`). Push events go main to renderer. Names in `IPC_CHANNELS` cover both. Payloads are structured-cloneable plain data. A secret is sent only on `keys:add` and `keys:replace`, and it is never a field on a result or an event (FR-11.11, NFR-5). `pages:readStart` may also send `suppliedText` (the page file the user picked, FR-2.9). That text is write-only. It is not a keychain secret, and it is not a field on a result or an event. Rejected calls name the channel and do not include the arguments.

`cap: null` means no cap. `projectIds: []` means the key is available to every project. `unchecked` means a saved key has never been tested. Country is stored as two uppercase letters, the shape of an ISO 3166-1 alpha-2 code. Language is an ISO 639-1 or BCP-47 tag with a lowercase primary subtag (`en`, `pt-BR`). Display labels are derived in the UI. The engine lowercases the stored country for SerpApi `gl` and lowercases the language tag for `hl`.

A provider can store more than one key. `keys:add` appends the new key after that provider's current rotation order unless `rotationOrder` is set. `keys:reorder` replaces that order. `keys:remove` deletes the keychain item and numbers the remaining keys of that provider from 0.

## Channel notes

**Onboarding.** Steps are `profile`, `serpapi`, `claude`, `jina`. `currentStep` is the first step still `pending`, or null when `finished` is true. Profile is `done` after a successful save. SerpApi is `done` when a SerpApi key is stored. Claude is `done` when a checkup has been stored or an Anthropic key is stored (section 15: the API key is the alternative). Jina is `done` when a Jina key is stored, and `skipped` when finish runs without one. `onboarding:finish` requires a saved profile and a saved SerpApi key. It does not require the checkup to be `ready`, and it does not require a Jina key (the Claude screen keeps Continue on the logged-out and missing states; Jina is optional). Finish is both "Finish setup" and "Skip for now".

`onboarding:saveProfile` writes the first project (name, domain, subdomains, brands, competitors, default market) and writes the person's name to `settings.userName`. `OnboardingProfile.userName` echoes that setting. It is not a project column. When the app-wide default country and language are still null, the save also seeds them from this market so Settings shows the same default. A later `settings:update` is not overwritten. City matching (FR-9.5) happens on this save: `defaultMarket.serpapiLocation` is the matched SerpApi name, or null when it did not match. The profile step does not ask for device or local wording. `device` defaults to `desktop`. `includeSubdomains` defaults to true. `localWording` is stored by the engine; the add-market screen (FR-9.6) is where the user chooses it.

**Keys.** Providers are `serpapi`, `jina`, `anthropic`, and `youtube`. `anthropic` is the `api_keys` row. `anthropic-api` is the Claude connection id (section 5.1), not a row provider. Responses carry `keychainRef` and `hint` (the last 4 characters, or empty when the secret is shorter than 4). `keys:test` takes an id and reads the keychain. It does not take a secret. An empty Jina field is not a test: the "no key, lower rate limits" line is local UI (FR-2.5). SerpApi usage on the returned key is `serpapiUsage`: `used`, `planLimit`, and `plan` from the account endpoint (SERP-7). That plan allowance is not the user's `cap`. The onboarding budget and the Settings "Monthly search budget" are `cap`, set on add and changed with `keys:setCap`. `keys:replace` is the Settings "Replace key" control. FR-11.6 tests an Anthropic key on save: the engine does that inside `keys:add` and returns the key with `state` already set. The Test button calls `keys:test`. `KeyTestResult.reason` is null when the test is `ok`. Otherwise it is `rejected` (401 or 403), `out_of_searches` (SerpApi plan with nothing left), `rate_limited` (429 after the retries), `timeout`, or `other` (a malformed body, a missing keychain item, a network error, or anything else). Every key on `connections:getOverview` includes `lastReason` (required; the value may be null). It is that same code when the cached `state` is `warning`, and null when `state` is `ok`, `unchecked`, or `off`. A later successful test or provider call clears it (FR-11, SERP-7).

A provider may have several keys (FR-11.1, FR-11.2). The same channels work for Jina: page reads try each Jina key that is on, in rotation order, and a key Reader refuses (401, 403), that is out of credit (402), or that is rate-limited (429) moves the read to the next key; after the last key Reader is called without a key at the lower rate limit (FR-11.5). A page or server failure does not move on. `keys:update` changes `name`, `plan`, `monthlyCap`, `enabled`, and `projectIds`. Omitted fields stay as they are. There is no `keys:setProjects` channel. `projectIds: []` means every project. `enabled` and `monthlyCap` are read-only copies of `on` and `cap`. `keys:update`, `keys:setOn`, and `keys:setCap` write `on` and `cap`, and `keys:list` reads the copies back. `enabled: false` keeps `rotationOrder`; rotation skips that key. `plan` is the user-entered name. App migration `015_api_keys_plan` adds nullable `api_keys.plan` for it. It is not `serpapi_plan`. When the user has not set one, a SerpApi response shows the account plan. `keys:reorder` takes `{ provider?, ids }`. `ids` must be exactly that provider's current ids, once each, or the call is rejected. The response is those keys in the new order, numbered from 0. `keys:remove` deletes that key's keychain item and closes the gap in `rotation_order`.

Every key result also carries `maskedKey` (four bullets plus `hint`, or empty when `hint` is empty; never the secret), `enabled` (the same value as `on`), `monthlyCap` (the same value as `cap`), `planLimit` (SerpApi `serpapi_limit`, otherwise null), `usedThisMonth` (searches recorded for this month, SERP-6), `status` (the stored `state`: `ok`, `warning`, `off`, or `unchecked`), and `statusDetail`. `usedThisMonth` is compared with the lower of `monthlyCap` and `planLimit` when both are set. Near that limit, an `ok` key has `statusDetail` `Near cap`. At or over it, `At cap`. `status` stays the stored state. A stored `warning` uses the last failure instead: `Auth failed`, `Rate limited`, `Out of searches`, `Timed out`, or `Could not use this key`. These fields are optional on the type so existing renderer literals still typecheck. Main fills them on every key result.

**Checkup.** `ClaudeCheckupResult` has `binaryPath`, `version`, `login` (`logged_in`, `logged_out`, `api_key`, `skipped`), `roundTrip` (`ok`, `failed`, `skipped`), `durationMs`, `resolvedModel`, `ready`, and `nextStep`. `resolvedModel` is the model id from the round-trip CLI `modelUsage` map. When that map has several keys, it is the one with the most output tokens. It is null when the round trip did not run or `modelUsage` is absent. The engine stores it on the checkup row's `detail_json`, so `connections:getOverview` and `claudeCode:getCheckup` return the same value as the latest `claude_checkups` row. `rows` are the three lines the screen shows. The renderer shows `statusLabel`, `detail`, and `nextStep` rather than writing its own error text (NFR-10). `plan` is a plan name only (FR-24.3). `api_key` means Claude Code is logged in with an API key only, not a subscription login. The engine stores `api_key`. It does not map that login to `logged_out`. The login row is a warning, the round trip is skipped, and `nextStep` tells the user to log in with their plan or add an Anthropic API key in CiteFox. `claudeCode:runCheckup` with `binaryPath: null` uses the saved Settings path, or PATH and the usual install folders when that is null (LLM-1). A non-null path is for this run only. `claudeCode:openTerminal` opens a terminal so the user can run `claude` themselves (LLM-2). CiteFox does not start a Claude login. The round-trip prompt is the `-p` argument, not stdin (LLM-3 exception: Architecture, Providers / claude-code; PR #10, commit `ca36a0e`).

**Settings.** `AppSettings` is the M1 slice of section 9.2: `userName` (the person, null until the profile step), default market (country and language nullable until set; section 15 forbids a hard-coded country), re-check interval, samples, prompts per page, Claude binary path, calls at once, model, Claude provider (`claude-code` or `anthropic-api`), and Jina mode (`fallback` default, `always`, `never`). `defaultDevice` starts as `desktop`. `dataDirectory` is the app data folder and is not editable. Defaults shipped as constants: interval 14, device `desktop`, subdomains included, samples 1, prompts 10, Claude concurrency 2, Jina `fallback`, Claude provider `claude-code`, SerpApi rotation `in_order`. `serpapiRotation` is `in_order`, `spread_evenly`, or `project_keys` (FR-11.2), and `settings:update` saves any of them. A missing value reads back as `in_order`. In order uses each key up to its room, then the next. Spread evenly moves to the next key with room on every search, with one cursor for the whole app. Project keys uses only keys whose `projectIds` include the project. A project's dedicated key is its whole pool in every mode. The AI Overview follow-up always uses the key that made the search (FR-11.3).

**Capsule.** `searchesLeft` is what is still available this month. It is null when no tested SerpApi key has a plan allowance or a cap. Per key it is the tighter of the CiteFox cap minus CiteFox's own searches this month (`usedThisMonth`, from `key_usage`) and the plan allowance minus SerpApi's reported use, which covers the whole account and can include other tools (`serpKeyAllowance` in src/shared/domain/serp-allowance.ts, used by every screen). `issueCount` is how many of SerpApi, Claude Code, Jina, and YouTube are `warning`. The mock-up draws three dots; the payload has all four states so the shell can place them.

Connection roll-up: no key is `off`. A saved key that has never been tested rolls up to `unchecked`. Claude Code is `unchecked` until the first checkup, `ok` when the last checkup is ready, `warning` when that checkup needs a next step, and stays a connection even when the selected provider is `anthropic-api`.

**Projects.** `projects:list` returns every project, including `archived`. The switcher hides `archived` (FR-10.8). `activeProjectId` is engine state. Section 10 has no current-project column. `projects:create` switches to the new project. `onboarding:saveProfile` is still how the first project is created. `projects:create` is the later New project form, and it takes the FR-1.1 fields plus the default market. It is null when setup is finished. The check itself is not a channel here.

Searches left stay on `status:getCapsule`. `pages:add` does not return an estimate. `PromptSetView.nextCheck` is the estimate for the next check of a saved page, counting enabled prompts only (FR-3.8).

The fourth setup step starts with `checks:start` (FR-1.7). `setupStep` stays `check` until that job finishes.

**Pins.** `pages:pinned` is oldest pin first, top to bottom. `label` is the short sidebar name. Null means the UI uses the title, then the URL. `score` is the default-market visibility score and is null until a check exists (M3). FR-20.9 is why the score is on the row now.

**Read page.** `reader: 'auto'` follows Settings `jinaMode` (FR-2.5). `jina` is "Read with Jina Reader instead". `direct` forces a normal fetch. "Read again" sends `auto`. `file` is FR-2.9 and requires `suppliedText`. The renderer reads the file with a file input. This channel does not open a dialog. A failed read still resolves. `message` and `nextStep` say what happened (NFR-10). The invoke rejects only when the call itself is invalid. Progress phases are `fetch`, `extract`, then `summary`.

`PageReadResult` is what the screen shows: status, title, meta description, H1, canonical, dates, outline, FAQs, word count, fingerprint, flags, and the promise summary. The body stays in the project database. `id` is the snapshot read id. `contentHash` is the full lowercase SHA-256 of the normalized body (FR-2.3). The UI may shorten it. Both `id` and `contentHash` are null when the read failed and no snapshot was stored. `snapshotReused` is true when this read reused an existing snapshot because that content hash was unchanged, and false when a new snapshot was stored. Title and meta flags use `TITLE_FLAG_LENGTH` (60) and `META_FLAG_LENGTH` (160). FAQ typos are on each `PageFaq.typo` (FR-2.7). `summary` is only on older snapshots. The read screen's quick actions (shorter title, what the page promises, check facts, check the claims online) are assists on `assist:run` (`page.shorterTitle`, `page.promises`, `page.checkFacts`, `page.verifyClaims`). The canonical page-wide list is `gaps:get`.

**Buyer profile.** One profile per page, the latest one (section 2.4). There is no pin for an older profile. `buyerProfile:generate` stores a new profile from the snapshot and a `buyer_profile` template. `templateId` omitted uses that kind's current app-wide default. The stored profile keeps `templateId`, `templateName` (the name at that run), `templateHash` (lowercase SHA-256 of the body that was used), and `templateUpdatedAt` (that template's `updatedAt`, null when the template had not changed since it was created). The id stays after that template is soft-deleted. `buyerProfile:update` saves a hand edit and does not change saved prompts or those template fields. `promptsStale` becomes true when a prompt set was written from an older profile. Sharpening and trigger ideas are assists on `assist:run` (`audience.sharpen`, `audience.triggers`). Adding a trigger is `buyerProfile:update`. Applying a sharpened part saves it with `buyerProfile:update`; Undo saves the previous part the same way.

**Prompts.** One active set per page (section 2.4). `prompts:list` returns that active set. `prompts:listSets` returns every saved set for the page, newest `createdAt` first. Each item is `id`, `createdAt` (ISO-8601 UTC, the same moment as that set's `savedAt`), `templateId`, `templateName`, `promptCount` (including disabled prompts), and `isActive`. `templateId` and `templateName` follow `PromptSetView`: both null when the set was not generated from a template, and `templateName` set when `templateId` is set. Exactly one set has `isActive` true when the page has a saved set. A page with none returns an empty `sets` list. `prompts:generate` and `prompts:save` make the set they write the active one. `prompts:setActive` makes the named saved set the only active set and returns that set as a `PromptSetView` with `dirty` false. It does not write a new version. An open draft is dropped. An unknown `promptSetId` rejects the call.

`dirty` means the `prompts` array is an unsaved draft and `version` is still the last saved version. `nextVersion` is what `prompts:save` will write. Save creates that version and starts a new baseline for every market on the next check (FR-3.6). The payload never uses the word "lock". `prompts:discard` drops the draft. `prompts:generate` stores the next version immediately. Hand edits (`add`, `edit`, `remove`, `setEnabled`, `reorder`) stay dirty until save. Rephrasing, more prompt ideas and the coverage check are assists on `assist:run` (`prompts.rephrase`, `prompts.more`, `prompts.checkPage`). Variants are one row per market (FR-8.6), including local wording. List, Cards, and Tree are views over this one list. They are not channels. The language picker filters variants in the UI.

`brandMessage` is the FR-3.3 sentence, including the brand names that were checked. Disabled prompts are included in that check and excluded from `nextCheck`. `enabled` defaults to true.

A set generated from a `buyer_prompts` template carries `templateId`, `templateName` (the name at that run), `templateHash` (lowercase SHA-256 of the body that was used), and `templateUpdatedAt`. All four are null when the set was not generated from a template. When `templateId` is set, `templateName` and `templateHash` are set. `templateUpdatedAt` is null when that template had not changed since it was created. `prompts:generate` takes an optional `templateId`. Omit it to use that kind's current app-wide default. The id stays after that template is soft-deleted.

**Gaps.** `gaps:generate` stores a `CoverageMatrix` for one run and returns it. A later call with the same content fingerprint returns that matrix with `reused: true` (FR-4.7). `stale` means the fingerprint has changed since `contentHash`. `contentHash` is the page body. `templateHash` is the template body. `gaps:get` is the latest run, or null. `coverage:list` is every stored run for the page, newest last, without the rows. `coverage:get` is one of those runs. Tracking and reporting compare runs by `runId`.

`gaps:generate` takes an optional `templateId`. Omit it to use the `coverage` kind's current app-wide default. The matrix records `templateId`, `templateName` (the name at that run), `templateHash` (lowercase SHA-256 of the template body that was used), and `templateUpdatedAt` (that template's `updatedAt`, null when the template had not changed since it was created). The id stays after that template is soft-deleted.

A row is one page and one prompt. `coverage` is `strong`, `partial`, `weak`, or `none`. `actions` is one or more of `update_existing`, `new_faq`, `small_update`, `optional_faq`, and `none`. A row can be both `update_existing` and `new_faq`. `whereCovered` is the list of places on the page. `currentContent` is what the page says now. `whatToUpdate` is what to change. `priority` is `high`, `medium`, or `low`. `suggestedFaq` is `{ question, answer, wordCount }` or null. `wordCount` counts the words in `answer`. `findings` are page-wide. The kinds are a closed list: `factual_claim`, `missing_promised_section`, `typo`, `title_length`, `title_meta_mismatch`, and `other`. `done` stays on the row (FR-4.6). `gaps:setDone` and `gaps:redo` return the whole matrix. Copying a draft is the renderer clipboard. It is not a channel.

**Templates.** Three kinds: `buyer_profile`, `buyer_prompts`, and `coverage`. A user can keep several named templates of each kind, edit them, and delete old ones. The rows are app-wide (FR-10.2). The default for a kind is app-wide as well. A project may override the default per kind with `projectSettings:update` (`templateOverrides`); a generation with no explicit template uses that override, and the app default once the chosen template is deleted.

Each kind has exactly one shipped template. Its name is `SHIPPED_TEMPLATE_NAME` (`CiteFox default`). `isShipped` is true only on that row. `templates:update` and `templates:delete` reject it with `shipped_readonly`. An app upgrade may replace a shipped template's body in place, on that same id. That changes `templateHash` and sets `updatedAt`. User copies are never touched by an upgrade. Their body, name, notes, hash, and `isDefault` stay as the user left them. Profiles, prompt sets, and matrices already stored keep the hash and name they recorded.

`name` is trimmed before the length check. After trim it must be 1 to 80 characters (`TEMPLATE_NAME_MIN_LENGTH`, `TEMPLATE_NAME_MAX_LENGTH`). A name that is empty after trim, longer than 80 after trim, or not equal to its trimmed form (leading or trailing whitespace) is rejected with `name_length`. The stored name is never untrimmed. Among live templates of one kind the trimmed name is unique, compared case-insensitively. `notes` is a string or null, at most 500 characters (`TEMPLATE_NOTES_MAX_LENGTH`). `body` is the Nunjucks source. `templateHash` on the template is the lowercase SHA-256 hex of that saved `body`. `createdAt` is when the row was created. `updatedAt` is null until the row changes after that. `deletedAt` is null while the template is live. `variables` are the supported names that occur in `body`. `warnings` are unknown `{{ name }}` tokens. They are not errors. The row also keeps `schema` and `settingsJson`. Those columns are not on `GenerationTemplate`. `version` is on `GenerationTemplate`. It is the integer stored on the row. A new template starts at 1, including a duplicate made with `fromId`. `templates:list`, `templates:get`, `templates:create`, `templates:update`, `templates:delete`, `templates:restore`, `templates:reset`, and `templates:setDefault` return that stored value. `templates:update` returns it after adding 1. Delete and restore return the value they found.

Exactly one template of each kind has `isDefault` true at all times. It starts as the shipped template. A deleted template is never the default. `templates:setDefault` moves the default inside that kind in one step. It rejects a deleted id with `deleted`. Setting the current default again returns that template.

`templates:list` takes optional `kind` and `includeDeleted`. Omit `kind` for every kind. `includeDeleted` defaults to false. Shipped templates come first, in kind order (`buyer_profile`, `buyer_prompts`, `coverage`). The rest follow by name, compared case-insensitively, then by kind, then by id. `templates:get` returns one template, including a soft-deleted one, so a stored id can still be opened.

`templates:create` takes `kind`, `name`, and either `body` or `fromId`. Not both, and not neither (`body_or_source`). `fromId` copies that template's body. The source may be shipped or soft-deleted, and it may be another kind. The new row uses `kind`. It is not shipped and it is not the default. `notes` omitted or null stores null.

`templates:update` takes `id` and any of `name`, `body`, and `notes`. Omitted fields stay. `notes: null` clears notes. It rejects a shipped template and a soft-deleted template. It keeps the same row id. It copies that row's `schema` and `settingsJson` through unchanged and sets `version` to the previous `version` plus 1. A name change uses the trim and `name_length` rule above.

`templates:delete` sets `deletedAt`. It does not remove the row. It rejects a shipped template with `shipped_readonly`, including when that shipped template is still the default. It rejects any other current default with `default_in_use` and the sentence "Set another template as the default before deleting this one." Set another default first. Deleting a template that is already deleted returns it unchanged. `templates:restore` clears `deletedAt`. If another live template of that kind has the same name, ignoring case, restore rejects with `name_taken`. Delete and restore copy `schema` and `settingsJson` through unchanged and leave `version` as it is. Duplicating the shipped template (`templates:create` with `fromId` of that shipped id) is how a user starts again from the shipped text.

`templates:reset` stays on the allow-list as a deprecated alias so current callers still typecheck. It takes `TemplateIdRequest` and returns that `GenerationTemplate`. It does not copy the shipped body onto a user template, and it does not move `isDefault`. New code does not call it.

Syntax is a small Nunjucks-compatible subset rendered by `src/shared/template-syntax.ts`, not Nunjucks itself: `{{ name }}` and `{# comment #}` only. Tags (`{% %}`), filters, and expressions are a syntax error, and nothing in a body is evaluated. A name is read only as an own key of the render context, and a dotted name renders blank with a warning. The supported variables are `TEMPLATE_VARIABLES`, written `{{ url }}`, `{{ title }}`, `{{ meta_description }}`, `{{ h1 }}`, `{{ page_text }}`, `{{ brand_name }}`, `{{ prompt_count }}`, `{{ outline }}`, `{{ faqs }}`, and `{{ last_modified }}`. `outline` is the H2/H3 headings as indented lines, `faqs` the numbered FAQ pairs, and `last_modified` the page's modified date or a sentence saying it is not stated. `page_text` is cut at a paragraph break after 60,000 characters. Whitespace around the name is optional, so `{{url}}` is the same variable. `templates:create` and `templates:update` save when the body contains an unknown `{{ name }}`. Those names come back in `warnings` and on the saved template. They are not errors. A Nunjucks syntax or render error rejects the call with `syntax`. The rejection names the channel and does not echo the body.

Other rejections are a `TemplateContractError`. `code` is a `TemplateErrorCode`. `message` is the matching sentence in `TEMPLATE_ERROR_MESSAGES`. The string form is `${channel}: ${message}`. The message does not include the arguments. `name_length` is a name that is empty or longer than 80 characters after trim, or that still has leading or trailing whitespace. `notes_length` is the notes limit. `name_taken` is the case-insensitive clash among live templates of that kind. `not_found` is an unknown id. `kind_mismatch` means the template's kind is not the kind the call asked for.

`templates:usage` counts saved artifacts that still point at that id: `buyerProfiles`, `promptSets`, and `coverageMatrices`. It does not count playground runs. Those stay in memory and are dropped on quit. Omit `projectId` to count every project. Set `projectId` to count one project. An unknown project counts as zero. The filter does not choose a project template. The default stays app-wide per kind. `lastUsedAt` is the latest timestamp among the counted artifacts, or null when every count is zero. A soft-deleted template still has usage. Saving a playground run into a project counts the saved parts, not the in-memory run.

`templates:usageDetail` takes the same request and lists those artifacts (`kind`, project, page, `savedAt`, `templateHash`), newest first, so the Templates usage line opens exactly the rows behind its count.

**Playground.** `playground:run` takes any URL. The URL is not a project page. Pass `templateId` for one template, or a non-empty `templateIds` for 1 to `PLAYGROUND_COMPARE_LIMIT` (3) templates of the same kind. Not both (`selection_conflict`). An empty `templateIds` array is the same as omitting that field. It is not an error, it is not `compare_limit`, and it does not raise `selection_conflict` with `templateId`. The engine then uses `templateId` when that is set, and otherwise that kind's current app-wide default. `kind` is required only when `templateId` is also omitted. Omitting `kind` in that case is `selection_required`. More than 3 ids is `compare_limit`. Different kinds are `kind_mismatch`. A deleted id is `deleted`. The response is `PlaygroundRunResult[]`, one run per template, in the order requested. One template is a one-element array. `overrides` may replace `body`, `promptCount`, and `brandName`, and they apply to every template in the call. Null means the saved template and, for the brand, whatever the run was given. Each run has the rendered prompt, the model text, `resolvedModel`, `usage`, `durationMs`, `templateId`, `templateName` (the name at run time), `templateHash`, and `templateUpdatedAt`. `templateHash` is the lowercase SHA-256 of the body that was rendered, including an override. It can differ from the template's saved hash. `templateUpdatedAt` is the saved template's `updatedAt` and does not change because of an override. `usage` is `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheCreationTokens`, and `serpapiSearches`, so the runs can be compared side by side. It has no cost. `serpapiSearches` is 0 when that run did not call SerpApi. A Nunjucks syntax or render error rejects the run. Unknown variable names come back on `warnings`.

The run is ephemeral. Unsaved runs stay in memory until quit. The engine keeps the most recent `PLAYGROUND_MEMORY_RUNS` (20) and drops the oldest beyond that. A compare counts as one entry per template. Playground runs are not part of `templates:usage`.

`playground:checkAio` checks one or more prompt strings against SerpApi for that URL. Each prompt returns `keyId` and `keyLabel` for the SerpApi key that was used, or null when no key was chosen. The secret is never returned. On failure, `ok` is false and `reason` plus `message` are set. `reason` uses the `KeyTestResult` codes. `message` must not contain a secret. On success, `cited`, `citedSources`, `position`, and `summary` are set. `citedSources` is `{ url, domain, position }` for each cited source, with `position` starting at 1. The prompt's own `position` is the requested page URL's 1-based place among those sources, or null when that URL was not cited. `summary` is short text, not the raw response. `market` null uses the app default market. If that default is unset, every prompt is `ok: false` and no country is invented. A non-null `runId` attaches the check to that ephemeral run.

`playground:saveToProject` is the only call that writes the run into a project. `parts` names what to write, at least one of `pageRead`, `buyerProfile`, `prompts`, `coverage`, and `aioChecks`. The engine writes only those parts. A listed part the run does not contain writes nothing for that part and does not fail the save. The result returns the project id, the page id, the coverage `runId`, and the parts that were written.

**TextBolt reference.** The page `https://textbolt.com/blog/how-to-set-up-text-alerts-for-business/` is the reference test client. The conversation is in `Docs/textbolt-reference.md`. A later task must turn that reference into fixtures: a page snapshot, expected-shape fixtures for the buyer profile, the 10 prompts, and the coverage matrix, plus edge cases (title/meta mismatch, a title long enough to truncate, partial coverage, a factual claim, a typo, and a prompt that must not contain the brand). This contract does not add those fixtures. The reference conversation writes variables as `{url}`. This contract uses Nunjucks `{{ url }}`.

**Tray line.** `tray:getLine` is the sidebar sentence for one project (FR-24.8). `running` is false until the tray process exists. `pagesDueToday` counts tracked pages whose next check is today. A paused project reports 0. The renderer formats "Running in the tray" and "14 pages due today". The menu is `tray:getMenu`.

## Projects at scale

**Project settings.** `projectSettings:get` returns the project, every market (the default first), the search source, this month's usage, the Claude connection, default samples, template choices, and the database file (`path`, `bytes`, `pageCount`, `checkCount`). `projectSettings:update` saves each part that is present. `search` is `{ source, cap, capRule, dedicatedKeyId }`: `shared` draws from the shared keys up to `cap` (null is no cap); `dedicated` uses one SerpApi key, whose `projectIds` becomes `[projectId]` so shared rotation skips it for every other project. A key another project already dedicates is refused. The key a project stops dedicating serves every project again. The cap rule is `pause` (checks pause until the 1st), `notify` (CiteFox waits for you), or `allow_10` (the cap plus `floor(cap / 10)`). The rule is enforced in the same live cap gate for manual and scheduled checks, and a stopped check's `nextStep` says what the rule does. `usage.allowance` includes the 10%.

**Template choices (TPL-1).** `templateOverrides` (`{ kind, templateId }[]`) is a view over the project's versioned `template_overrides` (the template editor's table, FR-26.8): a step is listed when its current project version is based on a named template other than the app default. Saving a choice stores that template's body and settings as the project's next version of the step; leaving a listed step out resets it to the app default. A version written in the template editor from the default is not listed and is not touched. The old `project_options.template_overrides` column is no longer read or written.

**Claude per project (FR-11.7, LLM-10).** `claude` is `{ connection, keyId, fallback, fallbackKeyId, model }`. `connection` is `app_default` (Settings), `claude_code` (the one Claude Code login, LLM-9), or `api_key` with a named Anthropic key. `fallback` is `wait`, `switch_key` (with `fallbackKeyId`), `retry_later`, or `ask`. Every Claude call path uses it: generation, assists, Fill from website (with a project), and check reports. On a limit or a connection failure, `switch_key` sends the call to the named key and nothing fails; the other rules stop the call. A check report stopped by `wait` runs again after an hour, and by `retry_later` after 15 minutes; searches are never repeated. `ask` stops until the user acts. `model` null uses the app model. Key ids the connection and rule do not use are dropped. `connections:projectClaude` lists each project that is not archived with its Claude settings.

**Create, copy, duplicate, archive, delete.** `projects:create` takes optional `copySettingsFrom`, `search`, and `claude`. Copy settings copies the schedule (unpaused), the cap and rule, Claude, default samples, the current project template versions (`template_overrides`, each becoming version 1 in the new project), and notifications. It never copies pages, prompts, history, markets, a dedicated key, or the Slack webhook. `projectSettings:duplicate` creates "<name> (copy)" with the same domain, profile, markets, and copied settings, and leaves the active project as it was. Archive and restore are `projects:update` with `status`; an archived project is hidden from the switcher and the scheduler skips it. `projectSettings:delete` needs `confirmName` equal to the name, refuses while a check is running, removes the project row (its searches stay counted on their keys with no project), closes pooled handles, and deletes `projects/<slug>.sqlite` with its WAL, SHM, and migration backup. Shared keys and default templates are not touched. A key that served only the deleted project keeps that list, so it serves no other project. The result names the project that is active now.

**Find competitors (FR-10.9).** `projectSettings:findCompetitors` reads the stored captures from the 30 days before the latest one, with no search and no Claude call. Domains cited instead of the own domain (and its subdomains) are ranked by overviews. Carrier, help, reference, community, review, and public-sector hosts are kept with `likelyCompetitor: false` and a reason. `listed` is true when the domain matches the project's competitors, by domain or by bare name.

**Usage (FR-10.6).** `projectSettings:usage` reads `key_usage` for the local month, so its searches add up with Results and Connections. `sharedCapacity` sums the effective monthly limits of the shared keys that are on, or is null when one has no limit. `unassigned` is that capacity minus the caps of projects on shared keys, or null when one of them has no cap. `claudeCalls` come from `activity_events`.

**Activity (FR-11.10).** `connections:activity` counts searches, Claude calls, and Jina reads in the last 24 hours, and tells the latest event in plain words: a SerpApi rate limit, cap, or failover with the number of searches moved in the same burst, a Claude limit or fallback, or a Jina failover. `connections:activityLog` returns the same counts summed from the rows behind them (`entries`, newest first, with key and project names; a `search` row can hold more than one search), the stored events the latest sentence tells (`latestEvents`), and this month's searches per key and project (`keyMonth`, from `key_usage`) with the reset date. Details are redacted; no secret is returned.

### Template editor (FR-26)

Every Claude step is a `GenerationTemplateKind`: `buyer_profile`, `buyer_prompts`, `coverage`, `aio_gap`, `run_summary`, plus kinds other areas add. Run order and copy come from `TEMPLATE_STEP_ORDER` and `templateKindInfo(kind)`, which fall back for a kind they do not know, so a new kind lists and edits with no channel change. `aio_gap` and `run_summary` are shipped rows (`tpl-aio-gap`, `tpl-run-summary`) with the same bodies and hashes the check reports always used. Check steps render grouped names (`{{ page.url }}`, `{{ run.page_cited }}`, `templateVariablesFor`). An unknown grouped name skips that report step and never stops the check. `answer_shape` (`tpl-answer-shape`, Docs/REPORT-SPEC.md section 9) reads `{{ prompt_text }}` and `{{ overview_text }}`, runs after the check reports on stored overviews only, resolves through the same project-version path, and is cached by overview hash in the project's `answer_shapes` table. `playground:run` rejects it with `playground_kind`.

`templates:steps` lists every step in run order. `status` is `project` when the open project has its own version, `edited` when the app default is a user template, else `shipped`. `effective` is what the next run uses: the project version, else the app default. A `templateId` a user picks on a generate call still wins over both.

`templates:saveOverride` stores the next project version in the project database (`template_overrides`, TPL-1). Versions are never changed. `templates:resetOverride` marks every version of that step reset (they stay in the file) and the project goes back to the app default; the next save continues the numbering. `templates:update` accepts `settings`; every app save also writes a `template_versions` row, so a hash recorded on a past prompt set or check always names wording CiteFox still has. `templates:resetToShipped` copies the shipped body and settings into a user template as its next version.

`TemplateSettings` (FR-26.3): `model` (null = Settings), `language` (null = the market's), `promptCount` (null = the page's), `tone` (null = as written). Only settings in `templateKindInfo(kind).settings` apply; others are dropped on save. Buyer prompts never offer `search_short`: they stay long situational questions.

`templates:try` renders the draft body and settings once against the page's latest snapshot (page steps) or latest finished check in that market (check steps), validates the reply against the step's schema, and returns `matched` and `problem`. It writes no generation, profile, prompt set, coverage or analysis row. The call is still in `llm_calls`.

### Assists, Claude call log, Ask CiteFox (FR-25)

`assist:run` takes an assist id (`ASSIST_IDS`; areas may register more in main) and its inputs. Main gathers saved data only (`savedDataOnly`, `searchesUsed: 0`), renders the assist's task after the shared output rules (no causation claims, facts to re-verify in `verify`, unconfirmed details in [brackets]), calls the project's Claude connection through `resolveClaude`, and validates the shared reply schema. It writes nothing to the project; Apply, Add and Undo are the screen's own channels. `assist:describe` returns the label ("Claude · on your plan · about 6 s") with the duration taken from that assist's `llm_calls` history.

Every Claude call the engine makes (page setup, check reports, playground, assists, Ask CiteFox, Try it) writes one `llm_calls` row through the provider wrapper `withCallLog`: in the project database when the call has a project, else in app.sqlite. Prompts and replies are never stored. `llm:usage` sums today and this month in local time. `llm:calls` lists every logged call of one template kind, newest first (at most `LLM_CALLS_LIMIT`, 200; `total` counts all), for the Templates "Last run" drill-down.

**Ask CiteFox and the help docs.** `assistant:ask` reads `Docs/help/*.md` in main (`src/main/ask/help/`). The build copies the folder to `out/main/help`, which ships in app.asar; a dev run also reads `Docs/help`. No folder or an empty one is not an error. Each file's front matter (`id`, `title`, `screen`, `keywords`, `summary`) and its `##`/`###` sections are parsed once (read again when a file changes). For each question the sections are ranked locally (BM25 over word stems; heading, topic title and keywords count twice; the screen's own topic a little higher); no service is called. The top 3 go into the prompt as `H1`…`H3` (template variable `help`), with `check_facts` (checks finished, the next scheduled check, fixes logged). A how / why / where question the router left to `explain`, or one that asks why a screen is empty, goes to the `assistant_help` template, which now also reads the project's counted numbers; data templates get the same two blocks. The reply cites the H refs it used in `sources` (the ref pattern is `[RNPH]n`); main turns them into `help` (`[{ id, title }]`, the file name and its title; a help answer that cites none links its best topic) and `next`, the screen named by the first topic's `screen` when it is not the screen asked on (`{ section: 'questions', label: 'Open Questions' }`). `list` answers keep the filter engine and return `help: []`, `next: null`. The renderer shows "Read more: <title>" (opens the help drawer, `drawer=help&help.id=<id>`) and the next step as a link. Both fields are optional on the type for older literals; main always fills them.

`ask:question` asks Claude for `AskFilters` only, validates them, and runs a deterministic query over each tracked page's latest finished check per market. The answer text, chips and rows are built locally. `ask:filter` re-runs edited chips with no Claude call. Neither runs a search.

### Background page setup and notices

Pages tracked in bulk (Import pages, Track cluster or silo, the sitemap rules, All pages Track) become `setting_up`. At most Settings' Claude "calls at once" pages run together, and at most `pagesPerHour` (default 12, app migration 021 `setup_runner`) start each hour. ## M3+ channel notes

**Checks.** `checks:start` is Check now, the first check, and a follow-up. `pageIds` has at least one page. `marketIds` null checks every market on each page (FR-7.5). A market the page does not have is skipped. `promptIds` null checks every enabled buyer prompt. A list checks only those prompts and the run is `partial` (FR-14.6). Disabled prompts stay out. The engine picks `runs.kind`. It sets `baseline` when section 8 says this is the first full check in that market after a prompt-set version is saved, a market is added, or samples change. The request does not send `baseline`.

The invoke stays in flight and resolves with the `CheckJob` when the job is `finished`, `cancelled`, or `error`. The first `checks:progress` event carries `jobId` before the first search, and that id is what `checks:cancel` uses. Closing the window does not cancel the job (FR-5.6, NFR-17). `checks:get` is the snapshot for "View results so far" and for a window that reopens. `checks:listActive` with `projectId: null` is every project.

`done` and `total` count prompts × markets. A pair is done when its `analysis` step is `ok`, `warning`, or `error`. Samples sit inside the prompt row. `searchesMax` is prompts × markets × samples × 2. `searchesUsed` includes retries (FR-5.5). `monthUsed` and `monthLimit` are this project's month and its cap. The cap is null when the project has none.

Phases are `reread` (section 3, SCH-4), `search`, `aio`, and `analysis` (FR-5.6). An AI Overview step is still emitted when no follow-up token was present, so the table can show Loaded, Follow-up loaded, or No AI Overview. `errorCode` is `timeout`, `rate_limited`, `out_of_searches`, `rejected`, `token_expired`, `empty`, or `other`. `empty` after retries is an error, not `no_aio` (FR-5.5). `token_expired` is the SERP-3 retry still failing. `CheckJob.message` and `nextStep` follow NFR-10 and must not contain a secret. `message` is null unless the job `status` is `error`.

Each step on `checks:get` has `promptText`, the buyer question in that market's wording. `label` stays the short name (FR-5.6, FR-8.6). `error` on that step is a short sentence, or null when the step has no error. It must not contain a key, a token, or a raw provider payload (NFR-5, NFR-10). A step may have `error` set while the job `status` is still `running`.

`checks:progress` does not carry `promptText` or `error`. The Checking table reads those from `checks:get` while the job runs. The event still carries `detail`, `errorCode`, and `nextStep` for the step that just changed.

Cancel does not abort the provider call already in flight. That sample is stored if it returns. No later step starts. The job status is `cancelled`. In-flight work on pause is the same (SCH-11): running samples finish, waiting steps stay queued.

A job that would pass the project cap resolves as `error` and makes no searches when the cap rule is `pause` (SERP-2, FR-11.4). The invoke rejects only when the request itself is invalid. The rejection names the channel and does not include the arguments.

An interrupted job resumes from the last finished prompt and market (NFR-3). `checks:get` is how the renderer sees that. The engine owns the resume. There is no separate resume channel.

**Results.** One section 10 run is one page, one market, and one check. `results:get` is the Results screen for one of those. Null `marketId` is the page's default market (FR-9.8, FR-20.7). Null `runId` is the latest finished run. A running run id returns metrics from finished prompts only. Unfinished prompts are omitted. They are not `no_aio` and not `error`.

Section 7.1 points are `VISIBILITY_POINT_PAGE_CITED` (3), `VISIBILITY_POINT_OTHER_OWN` (1), `VISIBILITY_POINT_BRAND_MENTIONED` (1), and `VISIBILITY_POINT_NOT_CITED` (0). `no_aio` and `error` are excluded. The visibility score is points ÷ (3 × prompts with an AIO), nearest integer, 0–100. Null when no prompt had an AIO. With K samples, the prompt status is the most common one. A tie goes to the higher point value. `other_own_page` and `brand_mentioned` are both 1 point, so the earlier sample wins that tie. `error` loses to any other status. `frequency` is how many samples match that status, out of K. `position` on the row is the mean reference position of the citation that decided the status. Page `averagePosition` is the mean target-page position across samples that cite the target (section 7.2). `MarketCheckMetrics.promptSetVersion` is that check's saved prompt-set version, or null when the prompt set row is missing. It is not 0. `TrendPoint.promptSetVersion` is the same number or null.

`named` is independent of status (FR-6.4). It is true when the brand is in the overview text. Status `brand_mentioned` is that case with no own-domain link. `wrongPageCited` is status `other_own_page`. `citedUrl` is the URL that made `page_cited` or `other_own_page`. `references` is every source that overview cited for this prompt in the selected market, in position order (FR-6.3, FR-12.10, FR-13.2). It is the same `AioReference` shape as each sample on `checks:getPrompt`, taken from the sample whose status won. Empty when that prompt had no overview. `AioReference.untracked` is an own-domain URL that is not a tracked page (FR-20.5). Classification uses the project's `includeSubdomains` flag for own subdomains. `target` is this page, `own` is another own page, `competitor` is a competitor of the page's product (a topic: the topic's product; the project-wide list when it has no product or the product has no saved competitors), matched by domain and its subdomains or by name (`engine/checks/competitor-match.ts`), `other` is the rest (FR-6.5, prompt audit P9). The class is stored with the run: an old run keeps it when the lists change, and the leaderboard badge, Communities owners and report labels follow the stored class.

`movement` is against the previous check in the same prompt-set version and market (section 7.3): `gained`, `lost`, `improved`, `declined`, or `unchanged`. Null on the first check. `previousStatus` is that previous check's status, the same union as `status`. `previousPosition` is its 1-based citation position, or null when that status has no position. Both are null when there is no previous check. The renderer uses them for "Lost, was cited #2" (FR-7.2, FR-12.10, FR-13.1). `contentChanged` and `contentChange` are the fingerprint facts (FR-7.3). `wordsAdded` is signed. The summary sentence is for History. CiteFox does not claim the edit caused the citation change.

The funnel is five steps: `checked`, `aio_shown`, `own_domain`, `this_page`, `cited_and_named`. Each `promptIds` list is a subset of the step above. Each drop's ids are the difference, and `drop.count` equals that difference (FR-12.5, NFR-14). Buckets are `winning` (an own page cited AND the brand named, the report's "Already winning"), `cited_only` (an own page cited, brand not named), `named_not_linked`, and `invisible` (`opportunityBucketOf` in src/shared/report-copy.ts). They do not overlap, and together they are the prompts with an AIO. `no_aio` and `error` are in no bucket. `ugcOverlay` overlaps the buckets (FR-12.6). Every `promptIds.length` equals its `count`. The leaderboard counts AIOs, not links (FR-12.8). `overlap` and `gap` are null on the `you` row.

`comparison` is always three columns: baseline, previous, current (section 8). Missing checks are null fields, not omitted columns. Each column also has `promptsChecked`, the denominator beside `aiosShown` (FR-12.12, section 7.2). Baseline, previous, and current each carry their own count. It is 0 when that column's check does not exist. The other metrics on a missing check stay null. `stale` is true when `checkedAt` is more than `STALE_CHECK_DAYS` (7) before `builtAt` (FR-12.2). Times are ISO-8601 UTC. The renderer formats local time (NFR-15). `promptSetSavedAt` is when the prompt set in `promptSetVersion` was saved, the same moment as `PromptSetView.savedAt`. Null when `promptSetVersion` is null. The renderer prints "v2 · saved Sep 20, 2026" (FR-12.1). `runSummary` is the `run_summary.md` headline and body, or null. The count sentence on the screen is renderer copy from the bucket counts. `topActions` is read-only (FR-12.9). `text` is the title. `reason` is the line under it. `linkLabel` is the link wording. `screen` is where that link opens. Planning a fix is not a channel. "Explain this change", "What should I fix first?", and the brand sentiment tile are not on this payload. See M3+ decision 25.

`coverage` and `action` on a prompt row come from the latest gap matrix. `action` is `whatToUpdate`. Both are null when no matrix is stored. `stageRates` always include the rate. The renderer names best and weakest only for stages with 2 or more prompts (FR-12.11).

`results:history` is the trend, newest last, for one page and one market. Partial checks are included and flagged, and the chart leaves them out of the line (section 7.4, FR-14.3). `pageCitedRate` is page cited ÷ AIOs shown, null when no prompt had an AIO. Only finished runs are points.

`checks:getPrompt` is prompt detail. `samples` carry the redacted raw JSON (FR-5.3, FR-13.5). The engine removes `api_key`, `key`, and `token` from those strings before sending them (NFR-5). `aioText` is the stored overview, not a fresh fetch. `searchesUsed` is the sum of the samples. `otherMarkets` is each market's wording plus the latest status and position (FR-13.3). `aioGap` is null until `aio_gap.md` has run (FR-6.6). `whereCovered` is the gap row's list, or empty.

**Scores.** `PageSummary.score` stays the default-market visibility score and stays null until a check exists. `scores:listPages` is the same score plus `change`, `nextCheckAt`, and `lastCheckedAt` for the grid. A paused project does not clear a page's `nextCheckAt`. `scores:listProjects` is the Projects glance and the cards: average score, change, next check, searches used of cap, pages due today (FR-10.5, FR-20.2). `change` is current minus the previous check, not a calendar month. Pages with no score are left out of the average, not treated as 0. The average and the mean change are nearest integers. `searchesUsed` is this project's month from `key_usage`. `searchCap` null means no cap. On a paused project, `nextCheckAt` stays the next check after resume (SCH-9) and `pagesDueToday` stays 0. The UI reads `paused` and shows "Paused". `nextCheckAt` is null when no page is scheduled, or the project is archived. The glance `nextCheckAt` is the soonest of those times, including paused projects.

**Schedule.** `schedule:getApp` and `schedule:updateApp` are Settings → Schedule (SCH-1): start at login, catch up after sleep, "Also check when CiteFox is closed", and the app daily check time. `checkWhenClosed` true registers the OS job. False removes it. The job's command is `citefox --check-due` (section 11). That flag is not an IPC channel. It runs the same pass as `queue:checkDue`.

`schedule:getProject` and `schedule:updateProject` are the project's clock (SCH-9): default interval for new pages, daily check time, quiet hours, spread across the day, catch-up, and pause. Pages keep their own interval on `pages:update` (FR-1.4). `paused` true is pause for this project. False is resume. The UI reads `paused` and shows "Paused". Quiet hours are `HH:MM` local time. Null means off. A window that crosses midnight is legal. `nextCheckAt` is the soonest page, ISO-8601 UTC, computed by the engine, and it stays set while the project is paused. That instant is the next check after resume. It is null when no page is scheduled, or the project is archived. `pagesDueToday` stays 0 while `paused` is true. Daily check time is the computer's local timezone. There is no per-project timezone in this contract.

`schedule:listDue` is the due list. `projectId` null is every project. A page is due when it is `tracked`, the project is not paused, and `nextCheckAt` falls on the local today or earlier. Leaving a paused project off this list does not clear its `nextCheckAt`. `reason` is `scheduled`, `follow_up` (SCH-10, and `promptIds` is set), or `catch_up` (SCH-3, outside quiet hours). `fixId` is set only when `reason` is `follow_up`. `day` is that local date as `YYYY-MM-DD`.

`FixFollowUpInput.description` is what changed (FR-14.5) and is required. The fix number is not on this input. Storage assigns the next number for that page, and only the stored record carries it. `FixFollowUpInput` has no `completed` field. Completion is `followup_run_id` being set (SCH-10). The FR-14.7 verdict stays its own field.

**Queue and tray.** `queue:getStatus` is running and waiting counts, tray and headless-job flags, next run, pages due, Claude concurrency and how many Claude calls are in flight, per-key usage, and per-project cap, cap rule, and dedicated key (SCH-11, FR-11.4, FR-24.4, LLM-7). `claudeConcurrency` is the Settings value. This channel does not change it. No SerpApi requests-per-second setting is added. A rate limit comes back as `rate_limited` (FR-11.3). Cap rule, cap, and dedicated key are readable here and are not writable in this contract. `nextRunAt` is null when the queue is `paused_all` or `paused_today`. A paused project does not clear `nextRunAt`, and it contributes 0 to `pagesDue`. The per-project `paused` flag is what the UI reads to show "Paused".

`queue:pause` takes `all` or `today`. Both let the in-flight sample finish and start nothing further. `all` stays until `queue:resume`. `today` clears at the next local midnight (FR-24.6). `queue:checkDue` starts due pages. A second call on the same local date does nothing (`started: false`, SCH-2) and returns the job ids from the pass that already ran. The tray and the headless job share that pass, so they cannot run the same check at once.

`tray:getMenu` is the menu facts: paused for today, pages due, pages waiting, and the last `TRAY_MENU_CHECK_LIMIT` (5) finished checks with score and change (FR-24.6). Open CiteFox, Quit, and Ask CiteFox are not channels. Ask CiteFox is M5. `checks:finished` is the desktop notification payload (FR-24.7): page label, page cited of AIOs shown, the change in the cited count, the default-market score and its change, and whether the content changed. The main process raises the notification. The renderer does not request a notification permission.

`queue:status` is pushed when `state`, `running`, or `waiting` changes, and when a search is counted. The payload is the same `QueueStatus` as the get.

**Email and alerts.** `email:getSettings` is the mode and the accounts. `smtp` sends while the tray runs. `mail_app` opens a draft and waits for a click (FR-23.1). `SMTP_PRESETS` fills host, port, and security for `gmail`, `microsoft365`, `ses`, `sendgrid`, `mailgun`, `resend`, `postmark`, and `other` (FR-23.2). The numbered setup steps stay UI copy. `email:saveAccount` sends `password` once. A create requires it. An update with `password: null` keeps the stored secret. The result is `EmailAccount`: `keychainRef` and no password (FR-23.3, FR-11.11). `email:test` reads the keychain and returns `ok`, `host`, `testedAt`, `message`, and `nextStep` (FR-23.4). The request is `EmailTestRequest`. `to` is optional. When it is one address, the test is sent there. When it is omitted, the test is sent to the account's from address. An invalid `to`, including a comma-separated list, is `Invalid request` and nothing is sent. Several accounts are allowed. `isDefault` marks the one projects use unless they pick another (FR-23.5).

`EmailAccount.usedFor` is filled in when the account is read. It is not stored on `email_accounts`. Each project whose alerts set `emailAccountId` to that account is one entry: `projectId` and a `label` of the project name. Each live report schedule whose `account_id` is that account is one entry: `projectId` (null for an all-projects schedule), `scheduleId`, and a `label` of the schedule name. A schedule with `deleted_at` set is left out. A null `accountId` uses the default account at send time and is not an entry. `usedFor` is empty when nothing names the account.

`alerts:get` and `alerts:update` are one project's notifications (FR-23.13): desktop, email after each check, recipients, sending account, Slack on or off, the monthly client PDF on the 1st, and `monthlyPdfTo`. A project with no stored alerts row returns `desktop: true`. Email, Slack, and the monthly PDF stay off. A stored `desktop` value is returned as stored. The column cannot be null, so there is no separate unset desktop. `slackWebhook` is write-only. Null leaves it. An empty string clears it. The result has `slackWebhookStored` and never the URL. `monthlyPdfTo` is `alert_settings.monthly_pdf_to` from project migration `014_alert_settings_monthly_pdf_to`. It is null or one address. Omit it to leave the stored value. Null clears it. A comma-separated list is `Invalid request`. It is not split into several addresses.

**Scheduled reports.** `reports:list` returns every schedule as a `ReportScheduleListItem`. `nextSendAt` is ISO-8601 UTC. It is null for an `on_change` schedule or a paused project. `reports:save` takes a `ReportSchedule` and returns that list row. `projectId` null is every project (FR-23.7). `accountId` null uses the default sending account (FR-23.5). `summaryStyle` is `standard` or `client_friendly`, or null when Claude does not write the summary (FR-23.10). Timing is `after_check`, `weekly` (ISO day 1 through 7 and a time), `monthly` (`1`, `15`, or `last`, and a time), or `on_change`. `on_change` has `events` (`lost_citation`, `gained_citation`, `score_drop`, `check_failed`) and `scoreDropPoints`. A drop must be greater than that number, not equal to it (FR-23.8). A new schedule is `active` (FR-23.12). `reports:setStatus` sets `active` or `paused`. A paused schedule sends nothing. `reports:sendTest` sends one test for `scheduleId`. `accountId` null uses the default sending account (FR-23.5). **Sitemaps and sync.** A project's sitemaps are found through `https://<domain>/robots.txt`, then `/sitemap.xml` and `/sitemap_index.xml` (`sitemaps:discover` with `url: null`). A URL adds that sitemap first. Indexes are followed three levels deep, at most 200 files and 100,000 page URLs per sync; a file is cut off at 20 MB (gzip included) and at 50,000 URLs. Every robots.txt and sitemap fetch goes through the page-read SSRF guard and follows redirects by hand. Tag, author, category and archive sitemaps start skipped (`lowValue`). A sitemap index cannot be skipped. Skipping a sitemap leaves its untracked pages out at once (`removed`); tracked pages stay. Only user-added sitemaps can be removed. The first read of a project is a baseline (`trigger: first_read`): every page is added as `not_tracked` and no rule runs. ## Decisions

Settled by the CEO. The earlier ambiguity calls stand where this list does not replace them.

1. The person's name is `settings.userName`, an app-level setting. It is not a project column. `onboarding:saveProfile` writes it. `OnboardingProfile.userName` echoes it. Null until that step is saved.
2. `includeSubdomains` stays on the profile request and the saved profile. It defaults to true.
3. `device` defaults to `desktop`. The profile step does not ask. The renderer sends `desktop`, and new app settings store `desktop`.
4. `UK` and `GB` are both accepted and stored as given. The engine lowercases the stored code for SerpApi `gl`. It does not translate one into the other.
5. A provider can store more than one key (FR-11.1, FR-11.2). `keys:add` appends unless `rotationOrder` is set. `keys:reorder` requires that provider's exact current id set. `keys:update` is the edit channel. `keys:remove` deletes the keychain item and renumbers the remaining keys from 0. A key that is off keeps its place in the order and is skipped. Every rotation mode can be saved.

7. The capsule `issueCount` is the number of `warning` states among SerpApi, Claude Code, Jina, and YouTube. `off` and `unchecked` are not issues.
8. The re-check interval default is 14 days.

Onboarding still does not ask for a key name (FR-11.1). The renderer supplies one.

## SRS ambiguities

Settled here so M2 can be built. Each one is a place the SRS and the mock-ups do not say the same thing, or do not say enough.

1. **FR-1.8 is in this contract.** Section 14's M2 list does not name "Fill from my website". The M1 contract left it until page reading existed. `projects:fillFromWebsite` is that call. Suggestions are not saved until create or update. 14. **Views are not channels.** List, Cards, and Tree (FR-3.8) are one `prompts:list` drawn three ways. Prompt search, sort, and filters on that screen are local. Brand prompts are M6.

These templates use `{{ url }}` and the other six names in `TEMPLATE_VARIABLES`. An unknown name warns on save and on a playground run. A syntax or render error still fails the call.

29. **A listed save part can be empty.** `playground:saveToProject` writes only the named parts. A named part the run does not contain writes nothing for that part and does not fail the save.
30. **Several named templates per kind.** Each kind has one shipped `CiteFox default`, which update and delete reject, and exactly one app-wide `isDefault`, which starts as the shipped template. `templates:reset` stays as a deprecated alias and does not copy the shipped body onto a user template. `templates:create` with `fromId` of the shipped template is how a user copies it.
31. **Usage counts saved artifacts only.** `templates:usage` returns `buyerProfiles`, `promptSets`, `coverageMatrices`, and `lastUsedAt`. It does not count playground runs. Omit `projectId` to count every project. The default template stays app-wide per kind.
32. **Upgrades replace shipped templates in place.** The shipped row keeps its id. User copies are not modified.
33. **Generate takes an optional `templateId`.** `buyerProfile:generate`, `prompts:generate`, `gaps:generate`, and `playground:run` use the kind's current app-wide default when no template id is given. For a playground run with no id, `kind` names which default. Stored rows keep the template id after a soft delete.
34. **A playground compare is one response of several runs.** A non-empty `templateIds` holds 1 to 3 ids of the same kind and is an alternative to `templateId`. An empty `templateIds` array is the same as omitting it and is not an error. The response is one `PlaygroundRunResult` per template, each with its own `usage`. Each of those runs counts toward the in-memory cap of 20.
35. **A page keeps every prompt set, and exactly one is active.** `prompts:list` is the active set. `prompts:listSets` is the history, newest first. `prompts:setActive` switches the active set and does not write a version. Generate and save make the set they write the active one.
36. **An unchanged page read reuses the snapshot.** `PageReadResult.snapshotReused` is true only when the content hash matched a snapshot already stored. A new snapshot sets it false.
37. **Template rows keep `schema`, `settingsJson`, and `version`.** Update, delete, and restore do not rewrite `schema` or `settingsJson`. Update adds 1 to `version`. Delete and restore leave `version` unchanged. `GenerationTemplate.version` is that stored integer. A template name is trimmed before the 1–80 check. An empty, too-long, or untrimmed name is `name_length`.

## M3+ decisions

The SRS is silent on these. Each one is the smallest rule that lets the channels be built.

1. A check job groups the section 10 runs for one `checks:start`. One run is still one page × market.
2. `runs.status` is `running`, `finished`, `cancelled`, or `error`. `partial` stays a separate flag and is true only for a follow-up.
3. `done` / `total` count prompts × markets. The progress bar does not count samples or phases.
4. Cancel and pause let the in-flight sample finish and store it. They do not start the next step.
5. Sample-status ties use the higher point value. A remaining tie uses the earlier sample. `error` loses to any other status.
6. The score is the nearest integer, 0–100. Null when no prompt had an AIO. Pages with no score are left out of a project average.
7. `change` is current minus the previous check in that market. It is not a calendar month.
8. `nextCheckAt` is computed by the engine in the computer's local timezone. There is no per-project timezone on these channels. Quiet hours may cross midnight. CEO Bot's ruling on #22: SCH-9 wins, so a paused project keeps `nextCheckAt` as the next check after it is resumed. `pagesDueToday` stays 0. The UI reads `paused` and shows "Paused". `nextCheckAt` is null only when no page is scheduled, or the project is archived.
9. A due-check pass is idempotent per local calendar date (SCH-2).
10. `paused_today` clears at the next local midnight. `paused_all` stays until `queue:resume`.
11. The tray menu lists the latest 5 finished checks (`TRAY_MENU_CHECK_LIMIT`).
12. One `checks:finished` notice is sent per page, using the default market, when that page's markets in the job have finished.
13. Raw SerpApi JSON is a string. The engine strips `api_key`, `key`, and `token` before it is sent. The contract does not freeze SerpApi's schema.
14. Cap, cap rule, and dedicated key are readable on `queue:getStatus` and are not writable here.
15. No SerpApi requests-per-second field is added. Rate limits use `rate_limited`.
16. Export `from` / `to` are inclusive local dates `YYYY-MM-DD`. Logo bytes are write-only and are not stored on an auto-export.
17. `exports:preview` and a blocked `exports:start` resolve. They do not reject. The block reason is the payload.
18. `citefox --check-due` is not a channel. It runs the same pass as `queue:checkDue`. SCH-8 (headless Claude via the API key) is an engine rule, not a payload.
19. Same rule as decision 8. The scheduler keeps `nextCheckAt` for a paused project (the next check after resume, SCH-9) and leaves `pagesDueToday` at 0. The UI reads `paused` and shows "Paused".
20. Archived projects are never due (FR-10.8). The scheduler reads `archived` from the project record. It is not a field on `ProjectSchedule`.
21. No SerpApi requests-per-second setting is added. When a provider reports `rate_limited`, the job is requeued rather than failed. The wait is Retry-After when that header is present, otherwise exponential backoff. Both waits are capped at the engine retry cap (`RETRY_DELAY_CAP_MS`, 30 seconds).
22. `pause` and `notify` both refuse new searches at the project cap. `allow_10` allows `cap + floor(cap / 10)`. `notify` also emits a cap-alert hook, once per project per local month. Delivery is a later email task.
23. `spreadAcrossDay` runs due pages in batches of 5, one batch every 15 minutes, starting at the project's check time. A slot inside quiet hours moves to when quiet hours end. A slot that does not fit that local day moves to the next day's check time. `08:00`–`08:00` means quiet hours are off.
24. Pausing a project or a page stops scheduled checks only. Check now still runs for a paused page or project. While the queue is `paused_all` or `paused_today`, a Check now job stays queued until resume. Claude concurrency remains the only concurrency cap.
25. "Explain this change" (FR-12.14) and "What should I fix first?" are deferred to the Claude insight work. The brand sentiment tile (FR-12.4, FR-16) is M6. The renderer hides those sections until then. It does not draw placeholders. The Running screen's "Explain errors" essay is the same deferred insight work. The short per-step sentence is `CheckStepSnapshot.error` on `checks:get`. `checks:progress` does not carry it. `CheckJob.message` stays the job-level sentence and is null unless the job status is `error`.
26. `citefox --check-due` exit codes: 0 means success, nothing due, or the queue is paused. 1 means at least one page check failed. 2 means a cap stopped the run. If both happen, 2 wins. `queue:checkDue` while the queue is paused returns `started: false`, enqueues nothing, and does not consume the day's pass. The day-pass marker is persisted (`getDayPass` / `setDayPass`) so the tray and a separate `--check-due` process share it. The caps ledger is seeded from month-to-date `key_usage` via `getKeyUsageForMonth`, not from zero. `--check-due` also reads `readAppSchedule` / `readProjectSchedule`, and writes `setPageMarketLastCheckedAt` and `appendTrayCheck` when a page check succeeds. Tests inject the same store interfaces.
26b. `--check-due` exits 0 without running when another CiteFox instance holds the single-instance lock. The normal app takes that lock on startup (`app.requestSingleInstanceLock()`) so a running window holds it. A second normal launch quits before it opens storage, the keychain, or a window, and the running instance focuses its window, restoring it first when it is minimised. A `--check-due` launch never focuses that window. While a `--check-due` pass holds the lock, a second normal launch is recorded and, when the pass ends, CiteFox calls `app.relaunch()` with the arguments minus `--check-due`, then `app.exit(code)` with the pass code. A second instance that is itself `--check-due` is ignored and does not relaunch.

## M3+ SRS ambiguities

1. **Section 10 `runs.status` has no values.** This contract uses `running`, `finished`, `cancelled`, and `error`.
2. **FR-5.6 "view results so far" needs a snapshot.** Progress events are one step each. `checks:get` is the table. A running run's score counts finished prompts only.
3. **The Projects screen says "change since last month".** FR-10.5 says "change" and section 7.3 is the previous check. `change` is the previous check.
4. **FR-12.3's headline sentence is two things.** Bucket counts are on the payload. The renderer writes the bold sentence. `runSummary` is the Claude text, or null.
5. **FR-12.9 "Plan as Fix N" has no write channel.** Top actions are read-only. Fix logging is M4.
6. **FR-22 lists HTML and JSON as well as PDF, XLSX, and CSV.** All five formats are on `ExportFormat`. Raw data is legal only for JSON.
7. **Report preview is not a channel.** `reports:*` and `deliveries:*` are the schedule, the change events, the test send, the soft delete, and the delivery history (FR-23.5, FR-23.7, FR-23.8, FR-23.10, FR-23.11, FR-23.12, NFR-16). FR-23.9 preview does not send and is not an invoke. The report screen itself is still renderer work.
8. **Open, Quit, and Ask CiteFox are not IPC.** The tray menu data is `tray:getMenu`. Ask CiteFox is M5.
